# DEMO_SCRIPT.md — 6-7 Minute Live Demonstration Script

## Overview
Target time: **6 to 7 minutes**.
Run the API offline with `python scripts/run_demo.py`, then start the web UI with `cd web && npm run dev`. The AI segment below uses the actual local YOLO checkpoint and a video clip, with the mock ESP32 so no command is sent to live Wokwi/Firebase. `make demo` runs the same offline API launcher.

---

### Step 1: The Problem (30 seconds)
- **Visual:** Fixed-timer intersection.
- **Narration:** Describe the delay problem and state that this project evaluates signal-priority behavior in simulation. Do not make medical outcome claims unless you add a credible citation.
- **Action:** Show the fixed-time baseline from a recorded simulation run and identify the seed and scenario shown.

### Step 2: The Live Moment (90 seconds)
- **Visual:** Dashboard Live Twin in the browser.
- **Action:** With the offline API running, execute `python vision/worker.py --mode live --video data/videos/istockphoto-936190804-640_adpp_is.mp4 --approach N --max-frames 100` from the project root. This requires the local `vision/weights/best.pt` and vision dependencies.
- **Observation:**
  - Show model output lines with frame number, predicted class, confidence, and `confirmed` state; the detection is generated by YOLO from video frames, not loaded from the replay JSON.
  - Explain that model inference and temporal debounce run on the host; the ESP32 receives the resulting approach-specific command and does not run the camera model.
  - At confirmation, show the `PRIORITY` action and the mock controller's safe transition. The Architecture tab explains where roadside cameras connect in a deployment; no real roadside camera is connected in this demo.
  - The FSM respects minimum green, transitions through yellow and all-red safely.
  - Only the ambulance's approach receives green; the other three approaches stay red during its priority hold.
  - The mock controller updates its phase and the dashboard displays the new state.
  - After detections stop, the priority engine sends `CLEAR` and the FSM resumes its safe cycle.

### Step 3: A/B Battle & System KPIs (60 seconds)
- **Visual:** Compare page in the dashboard.
- **Action:** Trigger side-by-side synchronized replay between Baseline and Priority mode.
- **Observation:**
  - Report the KPI values shown for the selected seed/scenario. Do not present a single run as a general result.
  - Include the effect on other approaches and recovery time where those KPIs are available.

### Step 4: Kill-Switch & Resilience (45 seconds)
- **Action:** Execute `python scripts/kill_switch_demo.py`. This is a local FSM demonstration, not a switch that disconnects the running API.
- **Observation:**
  - The simulated controller detects heartbeat expiration (>10s).
  - Mode transitions to `FALLBACK`.
  - Buzzer/status LED alerts, lights safely cycle normal fixed timer.
  - Invariants S1-S7 remain completely intact.

### Step 5: Security Attack Demo (60 seconds)
- **Action:** Run `python scripts/attack_demo.py`.
- **Observation:**
  - Test 1: Missing JWT -> 401 Unauthorized.
  - Test 2: Forged token -> 403 Forbidden.
  - Test 3: Detection flood -> Rate limit 429 Too Many Requests.
  - Test 4: Only claim HMAC rejection if `HMAC_ENFORCE=true` and the selected controller verifies signatures. Firmware does not currently implement that check.
  - Security dashboard displays recorded events from the configured store (in-memory by default; MongoDB when enabled).

### Step 6: Numbers & Model Metrics (45 seconds)
- Show model and latency metrics only if measured for the current weights and machine. The targets in `ARCHITECTURE.md` are goals, not established results.

### Step 7: Limits & Future Work (30 seconds)
